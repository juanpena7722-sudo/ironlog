# TB08 — Backup export/import API

- **Status:** Verified, PR #9 awaiting owner approval
- **Branch:** feat/tb08-backup-api
- **Date:** 2026-11-08

## Summary

Adds the backup API under `/api/v1/backup`. `GET` returns all of the current user's data as an
`AppData` v1 attachment named `ironlog-backup-YYYY-MM-DD.json`. `POST /import` accepts an
`AppData` v1 file up to 5 MB and either merges it (only new entries are inserted) or replaces
all of the user's data in one transaction. With `unitHint=lb`, weights are converted to kg and
inch measurements to cm before validation. The response reports imported and skipped counts.

### Cycle 1

Cycle 1 failed. A body nested about 10 000 levels deep in an unknown field, sent with
`unitHint=lb`, returned 500: the lb conversion copied the whole body with `structuredClone`,
which overflowed the stack. Cycle 1 also found that two imports racing for the same unused UUID
could fail with a unique-key error, and that the slowest near-5 MB import took 49.7 s.
Commit `a54ccfb` fixed all three (see Decisions).

### Cycle 2 probe

A throwaway probe (not committed) sent 125 requests to both routes and got no 5xx:

- Nesting 10 000, 100 000 and 1 000 000 levels deep (arrays and objects), with `unitHint=lb`
  and `unitHint=kg`, in an unknown top-level field, in unknown fields of a workout, body entry
  and goals (200, unknown keys stripped), and in place of every collection, item and weight
  field (400 with the path).
- Empty and invalid JSON, `text/plain`, `null`, number, string and array bodies, `__proto__` and
  `constructor` keys, `1e400` and `1e308` values with `lb`, NUL in ids and notes, a year `0000`
  date and repeated `mode` / `unitHint` query values: all 400.
- The same UUID repeated within a file (in any case), imported twice, into another user and
  with `lb`, in both modes: all 200. An export imported into another user with merge, replace
  and merge again: all 200. A bad cookie or a deleted user: 401.

One worst-case import (5 242 040 bytes, one exercise with 238 262 sets, `mode=replace`,
`unitHint=lb`) returned 200 in 39.7 s.

## Notes

### Decisions

These were decided by the coordinator during the task:

- **Ids.** A client id that is a UUID not used by anyone is kept (lowercased). A legacy
  non-UUID id, or a UUID another user already owns, is replaced with a new UUID. An id the
  current user already owns, or a UUID repeated in the file, means the entry is a duplicate and
  is skipped.
- **Goals per mode.** `replace` overwrites the goals with the file's goals. `merge` keeps the
  existing goals and counts the file's goals as skipped.
- **Health entries.** One per day: an entry whose date the user already has is skipped.
- **lb conversion before validation.** With `unitHint=lb`, weights are converted to kg and
  inch measurements to cm first, so the shared kg/cm limits apply to the converted values. Only
  the known weight and measurement paths are copied; unknown fields are never walked.
- **409 on a concurrent conflict.** If another request takes an id between the ownership check
  and the insert, the transaction rolls back and the API returns 409
  `Import conflicted with concurrent changes; retry`.
- **Timeout.** The import transaction has a 120 s timeout (`IMPORT_TIMEOUT_MS`).

### `shared/` NUL fix (owner approved)

Postgres rejects the NUL character in text columns, so a NUL in an imported name or note
caused a 500. With the owner's approval, `shared/schemas.ts` now has `textSchema`, which
rejects NUL; ids, names, notes, emails and passwords use it, so NUL returns 400 on every route.

### Known limits

- An export larger than 5 MB cannot be re-imported; the import returns 413.
- Merging the same legacy backup (non-UUID ids) twice creates duplicates, because legacy ids
  are replaced with new UUIDs and cannot be matched later (health entries are still skipped by
  date). Backups exported from the API use UUIDs and merge without duplicates.
- Timeout headroom: the slowest near-5 MB import measured 49.7 s in cycle 1 and 39.7 s in
  cycle 2, against the 120 s timeout. A slower database could reach it; the import then fails
  with 500 and nothing changes.
