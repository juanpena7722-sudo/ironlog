# TB06 — Body and health API

- **Status:** Verified, PR #7 awaiting owner approval
- **Branch:** feat/tb06-body-health-api
- **Date:** 2026-11-08

## Summary

Adds the body measurement API under `/api/v1/body` (list by date range, create, replace, delete)
and the daily health API under `/api/v1/health-entries` (list by date range, upsert by date,
delete by date). Every route requires a session and only touches the current user's entries.
Bodies and responses use the shared `BodyEntrySchema` and `HealthEntrySchema`. With the owner's
approval, `shared/schemas.ts` now caps every number that had no upper limit, so oversized input
returns 400 instead of 500.

## Notes

- **Verification cycle 1** passed every gate, but a probe found that `PUT /health-entries/:date`
  with `steps: 3000000000` returned 500: the value passed `HealthEntrySchema` and overflowed the
  `integer` column. Cycle 2 re-ran the full gate and a throwaway probe of 567 requests with
  oversized, tiny, fractional, non-numeric and boundary values on the body, health and foods
  routes, plus extreme dates and odd query strings. None returned 5xx.
- **Owner-approved `shared/` changes.** `shared/` is outside the task's files, so both changes
  were approved by the owner first:
  - `72d3aca`: `chest`, `waist`, `arms` and `thighs` are capped at 1000 cm
    (`MEASUREMENT_CM_MAX`). Before, any non-negative value passed and values above 9999.99 did
    not fit the `Decimal(6,2)` columns.
  - `82e1072`: every other unbounded number is capped. `steps` ≤ 200000 (`STEPS_MAX`, integer),
    `restingHR` ≤ 300 (`RESTING_HR_MAX`), `waterL` ≤ 20 (`WATER_L_MAX`, health and goals),
    `calories` ≤ 20000 (`CALORIES_MAX`) and `protein` / `carbs` / `fat` ≤ 2000 (`MACRO_G_MAX`)
    (foods and goals).
    The caps also apply to the frontend, which uses the same schemas.
- Health `PUT` is an upsert: it always returns 200, whether it created or updated the entry, and
  it replaces every field, so fields left out of the body are cleared. There is no 404 for PUT.
- Body `PUT` replaces the full entry too; optional fields left out are cleared.
- Body weights and measurements are stored as `Decimal(6,2)`, so values are rounded to 2 decimal
  places (for example, `0.005` is returned as `0.01`).
- There is no `GET /body/:id` or `GET /health-entries/:date`; the spec does not ask for them.
- The default `from` is 90 days back for body and 30 days back for health, and applies even when
  only `to` is given, as for workouts and foods.
